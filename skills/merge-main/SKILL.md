# Merge Main

Use for "merge main into this branch" or "finish merging main and fix tests". The remote is `origin`, the incoming ref is `refs/remotes/origin/main`, and the destination is the current named feature branch. Do not generalise this into a remote/base selection framework.

## 2. Establish the fixed integration boundary

### Fresh merge

Require a clean index and worktree, including no untracked user work, before a fresh merge. Ask the user to handle dirty work; do not stash or discard it. The coordinator may have added the exact `.elelem/` root ignore rule before creating workflow artefacts. Attribute and isolate that exact ignore edit separately from user work; if ownership or safe preservation cannot be proved, pause. Do not waive cleanliness for other changes, commit the ignore edit, or stage it implicitly. Verify the workflow path is ignored. If incoming changes touch the ignore file, block until the coordinator establishes an approved safe preservation procedure; do not remove the protection to make Git proceed.

In approved execution run `git fetch --no-tags --refmap= origin refs/heads/main:refs/remotes/origin/main`. If it fails, stop; stale remote-tracking refs are not a fallback. The explicit refspec requests only remote `refs/heads/main`; empty refmap disables configured opportunistic mappings and no-tags disables automatic tag following. Block effective fetch settings that could prune or update other refs. Do not add force, a leading `+` or destinations outside this exact target. Verify this invocation's FETCH_HEAD main commit matches the exact `refs/remotes/origin/main` commit ID; block on missing main, failed/rejected mapping or uncertain/mismatched evidence, even if an old tracking ref exists. Pin that full fetched ID as `incoming`. Capture the starting HEAD, branch and merge-base(s) with the pinned incoming commit. No common ancestor, unrelated histories or multiple merge bases require direction rather than an invented single base.

Before merge inspect effective Git configuration, including conditional includes, worktree settings and environment overrides, and hooks for unexpected side effects. If `merge.ff` is `false` or `only`, block. If `merge.autoStash` is `true`, block. For `branch.<current>.mergeOptions`, block any non-empty value, including `--squash`, `--no-ff` or `--autostash`, rather than guessing its interaction with this command. Unverifiable or conflicting settings block execution; ask the user for direction without persistent config writes or silent overrides. Distinguish a confirmed unset value from an inspection error: only verified normal defaults or explicit `merge.ff=true` and `merge.autoStash=false`, with absent/empty branch merge options, satisfy this gate. Recheck this gate if relevant configuration or environment changes.

Recheck branch, HEAD, operations, index and worktree against the recorded expected state after fetch and immediately before merge. Unexpected drift pauses dependent work; never silently rebaseline. Run `git merge --no-commit "$incoming"`, using the pinned ID, not the tracking ref. Normal fast-forward is allowed and moves HEAD immediately; do not automatically add `--no-ff`. Do not enable auto-stash, squash or automatic commits. A no-op leaves HEAD unchanged; a clean non-fast-forward normally leaves MERGE_HEAD and staged integration awaiting a merge commit.

Read command output and exit status, then inspect HEAD, MERGE_HEAD, unmerged entries and status. Distinguish real conflicts from unrelated merge failures, hook failures or partial operations; a non-zero exit does not itself establish a resolvable conflict. Stop on an unexplained failure. Record the actual no-op, fast-forward or pending-merge outcome, including any unexpected automatic commit, rather than concealing or undoing it.

### Existing merge

Pin current HEAD and exactly one MERGE_HEAD as the incoming target before editing. Capture index stages, existing staged resolutions and inherited unstaged/untracked contents. Confirm from accessible workflow/fetch evidence and branch purpose that this is the intended main integration. If provenance is unknown, ask the user and pause; never invent pre-merge cleanliness, ownership or a pre-merge baseline. The task-start snapshot is a resumed-state baseline, not the lost start of the merge.

Do not fetch to replace the resumed target, restart the merge or substitute a newer origin/main. A tracking ref that advanced does not invalidate an evidenced pinned MERGE_HEAD. Missing, malformed or multiple MERGE_HEAD values, or contradictory provenance, block dependent execution until resolved. Preserve all inherited integration changes, even when they span unrelated-looking pillars.

Preserve staged and unstaged contents separately, including partially staged files and already resolved paths. Do not restage an inherited resolved file just because it is in scope. If new corrections overlap an existing staged/unstaged boundary and exact preservation cannot be demonstrated, pause and ask rather than folding unstaged user edits into the index. Preserve unrelated untracked files; do not delete them as cleanup.

## 3. Reconcile intent, not conflict markers

For each conflicted path read the merge base and both sides at the pinned commits, branch purpose, surrounding contracts, callers and tests. Inspect index stages 1/2/3 where present; absent stages are meaningful for additions/deletions, not missing text to invent. Use merge bases and rename evidence for the whole integration, not just the conflict hunk. Never choose ours/theirs globally or use a blanket side-selection strategy.

Resolve autonomously only when evidence establishes the supported combined behaviour. Record path-specific rationale and distinguish inherited changes from new resolutions/corrections. For materially ambiguous behaviour, use `{{ASK_USER_QUESTION_TOOL}}` to ask a focused question and pause affected work. Do not infer a new requirement from whichever version happens to pass a test.

Handle add/add by reconciling both new contracts, and rename/delete by tracing identity, references and intended deletion rather than resurrecting or deleting blindly. For generated files identify the authoritative source and supported generator before changing output. For binary files identify ownership and an authoritative replacement or regeneration path. If evidence, tooling or authority is missing, ask; do not concatenate binaries, hand-edit unexplained generated output or pick a side arbitrarily.

The coordinator retains all Git/index mutation ownership, including staging. After inspecting the exact resolution and inherited index boundary, stage only explicitly resolved paths with `git --literal-pathspecs -C "$root" add -- "$path"`, where `root` is the verified repository root. Derive root-relative paths from NUL-delimited Git output; pass each as a quoted separate argument, with no wildcard expansion. Account for both paths of a rename or resolved deletion. Never use blanket staging, `git add -A` or `git add .`; path-specific staging is also unsafe when it would include inherited unstaged hunks. In that case use only an approved, demonstrated index-preserving method, otherwise pause. Recheck staged versus unstaged content after every index mutation. Workers return bounded edits and evidence, not Git writes.

Apply the same literal handling to path-scoped reads: use `--literal-pathspecs`, the verified root and quoted separate paths after `--` for `diff` and `ls-files` so attribution cannot expand to other files. `--` alone does not disable pathspec magic such as a filename `:(glob)*`. For committed blob reads use the pinned commit ID and exact root-relative tree path, not wildcard revision/path expressions.

## 5. Final state and handoff

Invoke `verification-before-completion` through `{{INVOKE_SKILL_TOOL}}` before any success claim. Check the final branch, HEAD and pinned incoming ID against the expected outcome, and confirm pending MERGE_HEAD still equals the pin when a merge remains active. For a fast-forward require HEAD equals the pinned incoming commit; for a no-op require the unchanged starting HEAD and evidenced incoming ancestry. Unexpected operations or identity changes block dependent actions and invalidate affected checks.

Inspect `git ls-files -u` for no unmerged entries, `git diff --check` and `git diff --cached --check` for hygiene, and actual final dirty/untracked state against the baseline and attributed edits. Check staged and unstaged preservation independently. Read required execution output and exit statuses against settled relevant inputs, including any required evaluations. Failed, skipped or unrun required gates prevent a success claim; report the bounded result as blocked or unverified. Do not conflate an empty diff with successful verification.

Do not commit or push. There is no automatic stash, rollback, merge abort, reset, branch switch or dependency installation on failure. Preserve the exact current state and ask for direction; specific destructive recovery requires separate explicit permission. A fast-forward has already moved HEAD and is not an uncommitted pending merge; do not promise otherwise or undo it automatically.

Report starting and current HEAD, pinned incoming commit ID, provenance/merge-base limits and actual no-op/fast-forward/pending-merge state. List resolutions and attributable corrective edits separately from inherited staged/unstaged changes, preservation limits, actual checks with exit statuses and valid input identities, unrun gates and blockers. State commit status explicitly: no automatic commit or push, and whether a merge commit remains pending. Report retained recovery artefacts if blocked; leave cleanup to the coordinator's registered-file procedure. A report is not independent review or integration acceptance.
